# 配置文件迁移：环境变量 → 配置文件

## 背景

img-search 与 img-val 最初通过环境变量管理调优参数：img-search 有约 12 个调优环境变量，img-val 有约 6 个。

随着参数数量增长，环境变量方案的痛点逐渐显现：

- **缺乏类型安全与范围校验**：布尔值需手写字符串转换，数值范围只能靠运行时隐式失败。
- **默认值分散**：默认值散落在各处的校验声明中，难以一览全貌，用户无法从单一来源了解全部可调项。
- **环境变量污染**：十余个带统一前缀的变量挤占 shell 环境，与 LLM provider 配置（`OPENAI_API_KEY` 等）混杂，难以区分用途。

## 核心决策

将全部调优参数从环境变量迁移至 TOML 配置文件，由各子项目加载。

- **配置文件路径**：位于数据目录下，文件不存在时使用全部默认值，不报错。
- **解析与校验**：TOML 解析后经 schema 校验（含类型约束、范围限制、默认值）。解析失败报配置错误，校验失败报告全部 issue。
- **保留的环境变量**：仅保留 LLM provider 配置（`LLM_PROVIDER`、`OPENAI_*`、`ANTHROPIC_*`）与数据目录定位变量。
- **配置为唯一来源**：迁移后的参数不再提供同名环境变量覆盖。
- 配置的具体文件命名见 [unified-data-dir.md](unified-data-dir.md)。

## 权衡分析

**方案 A：保留环境变量**（12-Factor App 风格）

- 优点：shell 友好，支持逐次调用覆盖（如在命令前临时设置某个调优变量的值再调用工具），无需额外配置文件。
- 缺点：十余个变量缺乏类型安全；默认值分散在转换链中难以维护；布尔值转换易错。

**方案 B：迁移至配置文件**（已选择）

- 优点：结构化格式，schema 校验类型与范围；默认值集中声明，自文档化；不污染 shell 环境。
- 缺点：丧失逐次调用的环境变量覆盖能力（用户需编辑配置文件）；新增 TOML 解析依赖。

选择 B 的关键依据：调优参数的特点是**数量多、类型多样（数值/布尔/字符串）、设置后很少逐次变更**。环境变量的逐次覆盖优势在此场景下收益甚微，而类型安全与集中默认值的收益显著。

## 影响范围

- **Breaking Change**：一批调优环境变量被移除，用户需将其值迁移到对应的配置文件中。
- 保留的环境变量不变：LLM provider 配置与数据目录定位变量。
- 配置文件命名遵循统一数据目录决策（见 [unified-data-dir.md](unified-data-dir.md)）。
