# tag-translator 提示词格式决策

## 背景（Context）

`tag-translator` 是一个独立的 Danbooru 标签批量翻译脚本（`tag-translator/index.js`）：按行读取标签列表文件，把每个标签翻译为中文并输出到新文件。翻译经 OpenAI 兼容的补全接口完成，不支持多模态、无结构化 JSON，仅依赖纯文本补全。

需要翻译的标签以文件形式批量到达，且要求**保持原始文件的行结构**——每一行形如 `标签=...`。这带来一个提示词组织问题：如何把"翻译一批标签"表达为 LLM 补全任务，同时让输出能稳定地回填到原行、避免对文件结构的破坏。

## 核心决策（Decision）

1. **增量补全（`标签=` 结构）**：每行以 `标签=` 作为 prompt 输入，要求模型只在 `=` 之后追加译文。读取时先把原行 `=` 之后的内容截掉，翻译完成后把返回文本追加为 `=译文`。输出文件逐行写回，保持与原文件行数一致。
2. **滑动上下文窗口**：翻译第 `i` 行时，把 `[max(0, i-60), i+1]` 行的原始标签块整体作为上下文输入（`lines.slice(...).join('\n') + '='`），而非单行或全量文件。`maxLineCount = 60` 由脚本顶部常量控制。
3. **prompt 措辞**：固定系统式开场——"你现在是一个标签翻译器，将以下danbooru中的标签翻译成中文，用=分隔。"——后接上下文块。
4. **解码约束**：`stop: '\n'`（首个换行即停）、`max_tokens: 35`、`temperature: 0.2`、`top_p: 0.65`；返回文本再截断到第一个 `\n`（`indexOf('\n')` 双保险）。

## 权衡分析（Trade-offs）

- **纯文本行格式 vs JSON 结构化输出**：当前格式为纯文本增量补全——输入直接用原始标签行（`标签=...`，零结构性包装），输出仅有译文本身，且在 `stop:'\n'` 处即止，无键名、引号、花括号、逗号等 schema 开销。若改为 JSON（如 `{"translation": "..."}`），每条输出需额外支付约 6–10 token 的结构化 token，对短译名（中文通常 2–8 字 ≈ 2–8 token）占比常超过 50%；输入侧若以 JSON 数组/对象包装标签行，结构性 token 同样逐行累加。批量翻译数万标签时，JSON 的格式开销随行数线性放大，纯文本增量补全因此显著更省 token。代价是解析依赖行结构与 `\n` 分隔约定，输出不具 JSON 的自描述性与模式校验能力。
- **`标签=` 增量补全 vs 输出完整行**：让模型只补 `=` 之后的内容，天然保证输出落在行内、不重排标签、不易产生游离换行；代价是每次调用都要裁剪输入行并重建 `=译文`，且依赖模型依从"只追加"的指令（配合 `stop:'\n'` 抑制越界输出）。
- **滑动窗口 vs 全量 vs 单行**：全量文件一次发送在标签量大时会超长且单点失败全损；单行无上下文则模型无法借助邻近标签风格保持译名一致。60 行滑动窗口在"上下文一致性"与"调用稳定性/成本"之间折中；代价是远端标签超出窗口时可能丢失跨窗口的译名一致性。
- **`stop:'\n'` + 截断双保险 vs 仅靠 max_tokens**：换行是行结构的天然分隔符，显式 stop 能尽早终止避免吞掉后续标签；再叠加一次 `indexOf('\n')` 截断作为补全异常输出兜底。

## 影响范围（Impact）

- 仅影响 `tag-translator/index.js` 自身的提示词构造与输出解析，不涉及仓库内其它工具。
- 输出文件格式约束：`<原名去扩展名>-tr<扩展名>`（如 `tags.txt` → `tags-tr.txt`），行结构保持不变。
- 本脚本为**遗留实现**：未接入 `@llm-image/shared` 的 LLM provider、未走 commander/统一数据目录，提示词与 provider 参数均内嵌。后续若纳入统一框架，本决策（增量补全 + 滑动窗口 + 解码约束）应作为提示词格式基线被继承，而非重造。
