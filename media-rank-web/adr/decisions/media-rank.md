# media-rank-web：通用媒体锦标赛排名组件

## 背景

img-cleanup-web 的手动加赛（LLM 未配置时的锦标赛）实现了一套「逐轮配对、
每对保留 1 张、轮空自动保留、候选 ≤ 目标收束」的交互，但与图片清理业务
（服务端会话状态机、`/api/image` 图片专用端点、URL 白名单）深度耦合。图片
之外的工具（音频选优、视频选优）需要同样的比较交互，因此抽离一个媒体无关
的公共组件。

## 核心决策

### 1. 独立 workspace 包，纯前端

`media-rank-web` 只含前端组件与状态机，无服务端。与 img-cleanup-web 同构的
栈：Cydon + UnoCSS/daisyUI 5 + Vite 8 (Rolldown) + TypeScript ESM + Vitest +
oxlint。`exports["."]` 直接指向 TS 源码而非 dist：消费方均为 Vite 应用
（组件模板经 Vite 的 `?raw` 导入，tsc 构建产物无法承载），避免为纯浏览器包
维护构建线。

### 2. 媒体源抽象：id/url → 直链接口

组件不加载媒体，只调用注入的 `MediaSource.getUrl(id, params)` 获取直链，
`params` 已知 `zoom`（缩略尺寸 px）与 `raw`（原始文件流），另有 `name`（该项
当前显示名），其余透传。这与
img-cleanup-web 的 `GET /api/image?u=…&w=…|raw=1` 端点同构（`w` → `zoom`、
`raw=1` → `raw`），迁移一个现有后端只需实现该接口。返回值直接用作
`img/audio/video` 的 `src`，代理端点、对象存储、data/blob URL 均可。媒体
类型由 `MediaItem.kind` 声明（缺省 image），决定渲染 `<img>`/`<audio>`/
`<video>`；`raw` 直链用于播放器与全屏查看层，`zoom` 用于卡片缩略图与悬停
预览（img-cleanup 的 `w=512`/`w=800` 语义）。

`name` 是为「直链按名字解析」的源准备的：playlist-rank-web 的 URL 模板把
「歌名 - 歌手」当输入，而用户在排名中改显示名，改的往往正是想听的那首
（歌手写错、歌名写反）。只按 id 取链会把旧歌放出来，于是把显示名一并交给源，
由源自己决定用哪个。id 始终是稳定标识：改它要丢弃裁决并回退重做（见 3e），
改显示名不会。

### 3. 锦标赛状态机客户端化，淘汰序即排名

img-cleanup 的加赛状态机在服务端（裁决要写 checkpoint 缓存），公共组件把
同构逻辑收敛为客户端同步纯类（配对/轮空/逐对裁决/收束），无 IO、可单测。
与 img-cleanup 的差异：收束后不只要保留集，还按淘汰轮次导出**完整排名**
（存活者最前、越晚淘汰名次越高）——比较过程的信息不丢弃。持久化不在组件
职责内：宿主监听 `rank-decide`/`rank-change` 事件自行记录（将来 img-cleanup
回接时可把裁决映射回 checkpoint 协议）。

**中断恢复（2026-09-30）**：配对经洗牌非确定，回放裁决记录无法重建同样的
对局，因此恢复以**完整状态快照**为契约——`rank-change` 事件携带
`toJSON()` 快照，`restore(snapshot, source)` 原样恢复（候选序/待裁决对/
轮空/轮次日志），宿主（如 playlist-rank-web）落 localStorage 即得刷新级
断点续排。快照与 img-cleanup 的 checkpoint 不同构：后者按 url 集合跨会话
复用裁决，前者只服务同一页面会话的中断续排。

### 3b. 淘汰赛升级为前 k 名提取（2026-10-01）

最初只有「淘汰赛」：逐轮配对、每对保留 1 张、轮空保留，收束时按淘汰轮次导出
分层排名。它的优点是裁决数最少（≈ n − target），但**名次只在轮次粒度上成立**
——同轮被淘汰者之间从未比较，相对顺序由裁决记录序填充。playlist-rank-web 的
真实诉求是「找出最好听的 5 首」，不是「给 40 首歌划出 5 个名次段」，分层名次
对导出播放列表毫无意义；而精确全排序（Ford-Johnson，≈ n·log₂n − 1.44n 次）
对 n=40 要比 ~100 次，代价又太大。

于是把 `target` 的语义从「目标保留数」改为**「找出前 k 名」**，并按 k 与候选数
n 的关系自动选算法（`mode` 成为派生状态，宿主不再手动切模式）：

- **k ≥ n（缺省）→ Ford-Johnson 精确全排序**：现有引擎原样保留。
- **k < n → 前 k 名提取**（`top-k.ts`）：先用**种子洗牌**（FNV-1a 哈希 id 播种
  xorshift）打乱候选做单败淘汰定出冠军（n − 1 次），再沿冠军的败者链用
  **胜者树**逐个提取次优（每次约 log₂n 次），直到凑满 k 名。总计
  ≈ (n − 1) + (k − 1)·log₂n，只保证前 k 名经比较链认证，k 名之后是提取过程的
  延拓（明写为「不承诺」）。

两个取舍值得记下：

1. **为什么洗牌**：确定性种子保证同一候选集总能洗出同一配对，快照只需存
   `{items, target, answers}` 三元组即可重放——与精确模式同构。若用随机源，
   恢复必须序列化配对状态机，快照体积和耦合都会上升。
2. **淘汰赛状态机（`tournament.ts`）保留**：它是 topK 冠军阶段的算法基础，
   也有 11 个单测覆盖轮空/逐轮推进/分层名次导出；只是不再由 element 直接驱动。

比较序列全部用 generator 表达（`MergeInsertionRunner`/`TopKRunner` 都是
`replay()` 重建），快照 = 候选集 + 目标 + 已完成裁决 id 序列。

**顺序约束（2026-09-30）**：playlist-rank-web 的多歌单场景要求「有序歌单
内部的相对顺序在最终排名中保持」。约束作为组件的可选入参
（`constraints`），收束时对锦标赛排名做**稳定拓扑重排**（每步取锦标赛序
最靠前的可行项）——约束未违反时与锦标赛排名一致，仅在被违反处局部调整，
锦标赛的人工裁决语义不被静默放大；约束成环时无解，宿主在开赛前用同一
纯函数（`applyOrderConstraints`）校验并提示检查输入。约束不进入配对
过程（受约束的对局仍会比较，人工裁决与歌单顺序相左时提醒但以约束为准），
避免为豁免配对引入配对算术的复杂度。

### 3c. 呈现改为播放列表：外壳可换，内核不可（2026-10-01）

需求是「把交互改成播放列表」。先做实测而不是直接改：用真实引擎（固定裁决以
稳定序列）dump 两种模式的比较序列，看相邻对是否首尾相接——这是「上一首 vs
下一首」这种听感流的前提。

```
FJ n=8:  i0~i1  i2~i3  i4~i5  i6~i7  i0~i2  i4~i6  i0~i4  i2~i4
         i3~i6  i3~i4  i5~i6  i1~i4  i1~i2        相邻相接 4/12
topK:    ...                                       相邻相接 8/18
```

相接率只有 1/3 ~ 1/2。FJ 的头几对是并列配对（彼此无关），之后是二分插入，
`i5~i6` 之后直接跳到 `i1~i4`——**播放列表要求的「上一首接下一首」在中途断裂。**

原因是排序算法的本质：任何比较排序都要求某些元素互不相关（配对轮），把它们
排成一条可连续播放的链，等于额外施加了「相邻关系已知」的假设——那不再是比较
排序，而是**验证一个既定顺序**（n−1 次）。反过来，播放列表若只作为呈现层包裹
比较排序，那层外壳是冗余的：外壳能做的事内核已经做了。

因此拆成两件事分别落地：

1. **呈现形态按媒体类型分流**（排序逻辑零改动）：音频一次只能听一个，并排
   两张卡没有意义——待裁决对与最终排名以**播放列表行**呈现（单列连续、序号 +
   内嵌播放器），排名完成后可直接连续播放（`playlistRows` + `playlistPlayer`，
   `ended` 自动接续，点任意一首从该首开始）。图片/视频能同屏并排对比，保留
   **两列卡片**布局。布局由待裁决首项的 `kind` 推导（派生状态 `audioLayout`），
   **暂不考虑同一对待裁决项混合多种类型**。这一层是纯呈现，拿到听感流的好处，
   比较次数不变。
2. **新增顺序校验模式**（`verify-order.ts`）：`start(..., verifyOnly = true)`
   只比较相邻两项、n−1 次，判定「后一首更好」处即逆序，**不改变**原顺序。这
   才是真正的「按播放列表听一遍」——因为它验证的本来就是链式顺序，所以天然
   首尾相接。它与排序不可比（求最优 vs 验证），但对「导入的已有歌单顺序对不对」
   这个真实场景，n−1 次比 n·log₂n 便宜得多。

### 3d. 播放衔接：跨对局复用「上一首」（2026-10-02）

校验模式天然首尾相接（比较的就是相邻项），但**排序模式不是**：实测 FJ 的相邻
对相接率只有 4/12、topK 8/18。这意味着一轮播完后，下一轮的第一首与刚播完的
那首通常毫无关系，「上一首 vs 下一首」的听感流会断。

解法是把衔接做成**呈现层规则**而非排序约束：新对局若包含上一轮展示过的歌曲，
该曲置首行标「上一首」且不重播，另一首从第二行渲染并单独播放。这既满足需求
（「本轮最后一首变为下一轮的第一首」），又在恰好重合时白拿播放共享的收益。

判定只用「新对局两首 ∩ 上一轮展示行」，不依赖引擎：两首都命中时取上一轮最后
一行衔接（最接近「上一首」的听感）；都不命中则不衔接（淘汰赛配对轮常见）。行序
与引擎比较序**解耦**——`onCardClick` 早已按 id 判定裁决，渲染顺序不影响结果。
因此这套规则对 precise 与 topK 同时生效，不为任一引擎写特例。

连播侧：`autoplayTick` 读 `pairCards[].carried` 决定起点（从新曲播起），
`advanceChain` 遇到衔接项跳过不播。原来的「精确模式 + 败者是上一对 a」判定被
替换为这个与引擎无关的规则，覆盖面更广（topK 的胜者树提取阶段同样受益）。

一处必要的状态管理：`start()`/`restore()` 要清空上一轮展示行（`resetChainState`），
否则新运行的第一对会与上一次运行的残留行误判为重叠。

结果连播用专用播放器（`playlistPlayer`）；对局连播没有独立播放器，直接顺序
播放待裁决两行**各自的行内播放器**——行节点在 sync 间原地合并、不被替换，
行内播放器的播放状态可靠，也省去一份需要与改名保持同步的标题状态；两者任一
开始播放暂停对方，沿用组件既有的单实例约定。

实现踩坑（两条都是实测抓到，读代码看不出来）：

- `VerifyOrderRunner.replay()` 最初在完成时提前返回空逆序表，导致「完成后
  读不到逆序」——单测抓到。逆序由已答裁决推导，与是否还有待比较无关。
- **同源双 c-for 曾导致点击失效（已在 cydon 修复）**：音频行与图片卡片最初
  写成两个循环，实测「第一次点击有效，之后全部无效」。根因在 cydon 的
  `for_`：每个 c-for 都对数组字段名 `Object.defineProperty` 一个访问器，
  同名第二次定义静默顶掉第一次——先注册的循环收不到任何后续数组更新，其
  上下文与事件处理器冻结在挂载时刻（cydon 仓库测试复现：更新数组后第一个
  循环停留在旧内容）。修复于 cydon `for_`：每个（实例, 数组名）只定义一个
  共享访问器，循环向它注册，写操作广播到所有注册循环；媒体侧模板随后恢复
  为自然的双 c-for 写法（回归测试覆盖整体赋值、原地变更与独立作用域）。

### 3e. 编辑已裁决项：丢弃裁决只能整段回退（2026-10-02）

已裁决的曲目此前锁死（`renameItem` 只认待裁决对里的项），因为改名/改 id 会与
裁决记录矛盾。现在开放编辑面板，但要回答「旧裁决怎么办」——这被日志结构直接
决定，几乎没有选择空间。

三个引擎的 `answers` 都是**位置日志**：第 i 条记录回答第 i 次比较，重放时逐位置
喂回生成器。所以「丢弃某曲目的裁决」**不存在就地删除的选项**——抽掉中间几条，
后续记录与比较立刻错位，重放会抛「裁决与比较不符」。唯一可行的是**整段截断**，
截断点取该曲目的**首次出场下标**。不是最后一次出场：后续每一步都建立在先前裁决
之上（FJ 主链、topK 阶梯皆然），只回退到最后一次会留下一段依赖未回退中间态的比较。
该推理落在 `verdict-log.ts`（纯函数 + 单测），三个引擎各自暴露
`comparisonsUpTo(n)`（定位首次出场）与 `discardVerdictsOf(id)`（截断）。

由此分出三类改动，语义差别很大：

- **只改名称/元数据** — 纯展示信息，裁决全留。可主动勾「丢弃原裁决」重来。
- **改 id** — 换了另一首（`MediaSource` 按 id 取直链），旧 id 在日志里已不成立，
  故**一律丢弃**、不受勾选影响。
- **重复 id** — 拒绝提交。id 是重放唯一键，重复即无法区分两条记录。

`topK` 的回退范围显著更大：**整表作废、从零开始**。这不是保守取舍而是结构约束
——淘汰赛签表由候选 id 派生种子确定性洗牌（`seededShuffle`），任一 id 变化都重排
整张表，先前裁决不再对应任何一次比较。精确模式与校验模式按位置配对，无此问题。
面板在该模式下显式提示这一点，不让用户以为只是退了几步。浏览器实测确认了这条
约束：topK 下改一个 id 后旧日志重放立刻抛「裁决与比较不符」。

实现上两个要点：

- 引擎持有 `start()` 时的 items 引用。改 id 后必须**重建引擎**并同时把新 id 写进
  items，只改 `data.items` 会让引擎与展示各持一份 id（实测：pairCards 仍渲染旧 id，
  后续裁决错配）。仅改展示信息则走 `sync()`，其 `latest()` 覆盖按 id 取到新名称。
- 面板输入框用 `c-model` 而非 `@change`——`@change` 在点「保存」时尚未提交，值
  根本没进状态（实测踩到：填了名字保存后名称未变）。`c-model` 逐键写入 `data`。

入口只放在**已看得见的已裁决行**（结果列表、校验逆序列表、对局的「上一首」行），
不新增「已裁决」折叠列表：进行中的对局只展示当前待裁决对，为看不见的项建界面
不划算。

### 4. Cydon 组件自带模板与依赖追踪边界

可复用组件不能依赖宿主页面提供模板（img-cleanup-web 的模板写在 index.html）。
组件在构造器中以 `?raw` 导入的模板字符串注入自身子节点，随后 Cydon 的
`connectedCallback → mount` 正常编译——Cydon 无 ShadowDOM 要求，light DOM
注入即可。

沿用 img-cleanup-web ADR 的全部踩坑结论（`c-show` 切换显示、`c-for` 列表
拍平、布尔属性用 `.prop` 绑定），并新增三条边界：

- **预绑定方法**：事件表达式与 `c-for` 克隆节点内的方法调用拿到的 `this`
  不可依赖（循环上下文/globalThis/代理），组件在 `connectedCallback` 把模板
  引用的方法 `bind` 到元素自身；绑定到 data 代理不可行——DOM 方法
  （`dispatchEvent` 等）经代理调用会 Illegal invocation。绑定后方法内状态
  写入必须经 `this.data`（响应式代理），直接在 `this` 上赋值不触发更新。
- **依赖追踪只认表达式直读**：绑定方法的内部读取不经过追踪代理。模板表达式
  引用的方法只能依赖**入参**（如同 img-cleanup 的 `rawUrl(url)`），组件状态
  （如当前查看的 `viewerId`）必须在模板表达式里直接读取，否则视图不更新。
- **点击即选、再点即确认**：音频/视频卡片内嵌原生播放器，原生控件吞掉点击
  与双击，img-cleanup 的「点击选中 + 双击确认」不通用；改为统一的
  「点击选中，再次点击同一卡片确认」，卡片底部按钮提供同一路径。

### 5. demo 页运行时合成媒体

demo 需要真实的图片/音频/视频验证三类渲染。仓库不提交二进制示例：图片用
canvas 合成（`zoom` 参数映射生成尺寸）、音频用 JS 合成 WAV（blob URL）、
视频用 canvas 动画 + `captureStream` + `MediaRecorder` 录制 WebM（初始化时
异步预生成，`getUrl` 保持同步；浏览器不支持时降级提示）。这也示范了
MediaSource 的 data/blob URL 形态。

## 后果

- 新增 workspace 成员 `media-rank-web`；img-cleanup-web 零改动。
- 组件为客户端状态机，img-cleanup-web 的加赛视图（服务端驱动）暂未回接；
  回接需组件支持受控模式（外部推进轮次），按需扩展。
- 排名算法有两档：k ≥ 候选数时付出 n·log₂n 换取严格全序；k < 候选数时只
  认证前 k 名，k 名之后无承诺。宿主若需要完整分层名次（如 img-cleanup 的
  「淘汰轮次 = 名次段」语义），k 应取 1 或用分层导出自行组装。
